# The Babo Violent 2.11 server: a specification for the Go rewrite

This is what the original server does, taken from the C++ source in `src/game/` (Daivuk/BaboViolent2 at
`7171c84`, the 2.11 "Pro" build: `_PRO_` defined). It is the input for openbv's Go server (`server/`), which
must reproduce the original rules exactly: same messages, same byte layouts, same timing, same formulas and
the same quirks, because the clients (openbv's port of the 2.11 client) keep their own copy of a good part of
the game state and only stay consistent if the server behaves as the original did.

Citations are `file:line` in `src/game/` unless another directory is given. "The server" means the C++
`Server` class plus the `Game`, `Player`, `Projectile`, `Weapon`, `Map` objects it owns
(`scene->server->game`). Where the listen server (a game hosted from the client, compiled without `CONSOLE`)
and the dedicated server (`CONSOLE` defined) differ, both are given; **the Go server reproduces the
dedicated (`CONSOLE`, `_PRO_`) build** unless stated otherwise, because that is what public servers ran.

Contents:

1. Architecture: who simulates what, the tick, the update order
2. The wire protocol: every message, grouped by phase
3. The baboNet layer and openbv's WebSocket transport
4. The map format (.bvm) and the map queries the server uses
5. Constants and formulas: weapons, projectiles, damage, scoring
6. Server cvars (`sv_*`)
7. Console commands for a dedicated server
8. Randomness, timing, non-determinism and quirks to preserve
9. The master server (game list) protocol
10. Go package structure and implementation plan, with differential testing

Appendix A (at the end) has the byte layout of every struct, generated by the compiler.

## 1. Architecture

### 1.1 Authority split

BV2 is a *client-trusting* design. The server decides some things, relays others, and trusts the clients for
the rest. In summary:

| Concern | Who decides | Notes |
|---|---|---|
| Player movement, collision with walls | **Client** | The client integrates its own babo (`Player::controlIt`, `Map::performCollision` on the client) and sends coord frames (§2.5). The server never runs player physics. |
| Position the server uses for hits | Server, from client frames | The server *interpolates* each player between the last two received frames exactly as remote clients do (`CoordFrame::interpolate`, `Player.h:78`, cubic with `cl_cubicMotion`, default true). Hit tests use this interpolated `currentCF.position`. |
| Speed-hack check | Server | Every 90 server frames, compares frame-ID progression and velocity (`ServerRecv.cpp:777`, §5.10). |
| Hitscan aim (SMG, DMG, CG, shotgun, sniper, photon, flame thrower) | Client gives origin and direction; **server** adds spread, traces the ray, finds the victim | In the Pro build the client sends a *direction* (`p2` = unit vector × 100), not an end point (`Game.cpp:1096`); the server applies random spread and range (`Game.cpp:1359`). |
| Fire rate | Server, loosely | Per-weapon minimum interval with tolerance (`ServerRecv.cpp:944`, `:1025`); melee (knives, nuke, shield, minibot) has **no** server-side rate check. |
| Projectiles (rocket, grenade, molotov, flames, items) | **Server** | The client asks for a projectile with origin and initial velocity; the server creates it, simulates it, detects hits and explosions, and deletes it (`GameSpawn.cpp:430`, `GameProjectile.cpp:234`). Clients simulate copies for display. |
| Damage, health, death | **Server** | `Player::hitSV` (`Player.cpp:1111`) applies damage and broadcasts the victim's *remaining life*; clients apply it with `Player::hit` and run the kill bookkeeping themselves. |
| Kills, deaths, score, team scores | Server, and **mirrored by clients** | No score messages exist for kills: each client recomputes scores from `NET_SVCL_PLAYER_HIT` (remaining life ≤ 0 → kill) with the same rules (`Player::hit`, `Player.cpp:950`). The Go server must send exactly the hits the original sends. |
| Item drops on death (life pack, weapon, grenades) | Server | Spawned as projectiles at death (`Player.cpp:1111`, §5.7). |
| Item pickups | Server | Life packs and grenades on contact; weapons on request (`NET_CLSV_PICKUP_REQUEST`). |
| Spawning | Client requests, **server** picks the spot | `NET_CLSV_SPAWN_REQUEST` → `Game::spawnPlayer` (`GameSpawn.cpp:144`) → `NET_SVCL_PLAYER_SPAWN` to all. The server does *not* check the respawn timer: the client waits `sv_timeToSpawn` itself. |
| Teams | Server | `NET_CLSV_SVCL_TEAM_REQUEST` → `Game::assignPlayerTeam` (`Game.cpp:880`), echoed to everyone, and every client runs `assignPlayerTeam` again on receipt. |
| CTF flags | Server | Pickup, return, capture by proximity, every server frame (`ServerCTF.cpp:24`); clients mirror the scoring from `NET_SVCL_CHANGE_FLAG_STATE`. |
| Round/game end, map rotation | Server | `Server::update` (`Server.cpp:566`). |
| Votes | Server | `Game::SVoting` (`Game.h`) plus `Server::validateVote` (`Server.cpp:121`). |
| Chat | Server relays | Team filtering done by the server (`ServerRecv.cpp:552`). |
| Cvars that affect play (`sv_*`) | Server | Sent to clients as console text `"set sv_x value"` (`NET_SVCL_SV_CHANGE`). |

### 1.2 The tick

The game runs at a **fixed 30 Hz step**: `dkcInit(30)` (`main.cpp`), `dkcGetElapsedf()` returns the constant
`1/30` (`src/engine/dk/dkc.cpp:42`), and the main loop calls `scene->update(delay)` once per elapsed 1/30 s
(several times to catch up). Every `delay` in this document is therefore `1/30 = 0.0333333…f` (float).
Many timers are counted in frames: ping (frames until pong; 1 frame ≈ 33 ms), `sendPosFrame`, `incShot`,
`damageTime`, `frameSinceLast`, `nukeFrameID`.

The Go server must run the same fixed step (a 30 Hz ticker, with catch-up), use `float32` arithmetic for all
game maths (the original is `float` throughout; double is used in only a few places, noted where it matters)
and process network input at the same point in the frame.

### 1.3 Order of one server frame

`Scene::update` (`Scene.cpp:173`) → `master->update` (master server connection) → `server->update(delay)`.
`Server::update(delay)` (`Server.cpp:566`), in order:

1. `infoSendDelay += delay`; when `> 20`: send the game row to the master (`sendServerInfo`, only if
   `sv_gamePublic`), reset to 0. (Starts at 15, so the first report is ~5 s after start.)
2. Finished account-auth HTTP requests: set `userID` (the account server no longer exists; openbv's curl
   shim fails every request, so this never sets anything; skip in Go).
3. Report uploads (skip).
4. Master ban answers (`BannedAnswers`) → disconnect banned players (only with a master that answers; skip
   unless the Go master implements cache bans).
5. *(Pro)* Checksum queries: each `CChecksumQuery::Update(delay)`; one older than 10 s without a reply
   disconnects the player (§2.2, `ChecksumQuery.h`).
6. *(Pro)* Delayed kicks (`delayedKicks`, from the camera-height anti-cheat; §5.10).
7. `updateNet(delay, false)` (`Server.cpp:440`): baboNet update; one connect or disconnect event per call
   (§3).
8. Map change countdown: `changeMapDelay -= delay`; at ≤ 0 do the map change (§2.8).
9. If `sv_gameType != game->gameType` → `game->resetGameType(sv_gameType)` (§2.8).
10. `gameTimeLeft -= delay` and `roundTimeLeft -= delay` when > 0, clamped at 0.
11. If `roundState == GAME_PLAYING`: check the end conditions per game type (§5.12); on end, set
    `changeMapDelay = 10`, pick `nextMap = queryNextMap()`, broadcast `NET_SVCL_GAME_STATE`.
12. Drain received messages: `while (bb_serverReceive(...)) recvPacket(...)` (§2).
13. Per player: ping/pong bookkeeping and timeout (§5.11).
14. Per player: max-ping enforcement, idle auto-spectate, the join message (§5.11).
15. `game->update(delay)` (`Game.cpp:348`): votes, players (only while `GAME_PLAYING`), photon beam ticks,
    weapon availability, minibots, projectiles (§5).
16. If `GAME_PLAYING`: coord-frame broadcast, per-player pings and the timer sync (§2.5).
17. Still inside that `GAME_PLAYING` block: auto-balance (TDM and CTF, §5.13).
18. Still inside it: the game-type update: CTF → `updateCTF` (§5.14); "Champion" (type 3) round timer
    (§5.15). (Steps 17 and 18 sit in the same `if (game->roundState == GAME_PLAYING)` as step 16,
    `Server.cpp:1228`; the original's indentation makes it easy to miss. So between rounds no flag is taken
    or captured and the auto-balance timer stands still.)
19. `updateNet(delay, true)`: a second baboNet update (again one connect/disconnect event).
20. Map transfers: up to `sv_maxUploadRate*1024/30` bytes of 250-byte chunks per frame (§2.3).
21. `frameID++`.

Note the two `updateNet` calls: with the original baboNet a connection accepted in step 19 gets its
`NET_SVCL_NEWPLAYER` and `NET_SVCL_GAMEVERSION` *after* this frame's broadcasts.

### 1.4 Players, IDs, babonet IDs

- Up to `MAX_PLAYER = 32` slots (`Game.h`); `sv_maxPlayer` (default 16) limits how many are used. A new
  connection takes the **lowest free slot** below `sv_maxPlayer` (`Game::createNewPlayerSV`, `Game.cpp:1644`);
  none free → disconnect ("server is full").
- `playerID` (0..31) is the slot; every message carries it as a signed `char`.
- `babonetID` is the transport's connection ID (positive, increasing). Clients send their own `babonetID` in
  coord frames; the server ignores a frame whose `babonetID` does not match the sender's (`ServerRecv.cpp:777`).
- **The server trusts the `playerID` field of client messages.** A client can send messages for another
  player's ID; the original accepts many of them (chat, team requests, spawn requests, shoot). Faithful Go:
  accept them the same way. *Recommended hardening (a deliberate, documented deviation):* map the sender's
  babonet ID to its player ID and ignore messages whose `playerID` differs. Make it a server option (default:
  on), since no legitimate client sends another player's ID.

Team IDs: `PLAYER_TEAM_SPECTATOR = -1`, `BLUE = 0`, `RED = 1`, `AUTO_ASSIGN = 2` (`Player.h`). Status:
`ALIVE = 0`, `DEAD = 1`, `LOADING = 2`. New players start as spectator, status `LOADING`.

## 2. The wire protocol

Every message is a baboNet packet: a 16-bit type ID plus a byte payload, which is exactly the memory of the
C struct (`sizeof`, padding included; layouts in Appendix A). All integers are little-endian; `char` is
**signed** (MSVC and our wasm32 client agree). Fixed-point conventions:

| Quantity | Encoding |
|---|---|
| Positions in coord frames, shots, projectiles | `short` = metres × 100 (truncation toward zero: `(short)(x*100)`) |
| Velocities | `char` = m/s × 10, truncated; range −12.8..12.7 m/s |
| `net_svcl_player_spawn.position`, `net_svcl_create_minibot.*` | `short` = metres × **10** (not 100; client divides by 10, `ClientRecv.cpp:465`) |
| Shot normal | `char` = component × 120 |
| Play-sound position | `unsigned char` = metres, truncated |
| Explosions, drop/flag positions, times, life, damage | `float` |
| Colour decals | `unsigned char` = component × 255 |

Encoding is truncation (C cast), not rounding; Go must use `int16(x*100)` on a `float32` value with Go's
truncation toward zero, which matches.

### 2.2 Connection and handshake

Sequence for a joining client (server side `ServerRecv.cpp`, client side `ClientRecv.cpp`):

```
transport connect
S  NET_SVCL_NEWPLAYER {newPlayerID, baboNetID}            to all (incl. the new client)
S  NET_SVCL_GAMEVERSION {21100}                           to the new client
C  NET_CLSV_SVCL_PLAYER_INFO {playerID, name, account user, md5(account pass) as 32 hex, MAC "xx-xx-..."}
C  NET_CLSV_GAMEVERSION_ACCEPTED {playerID, password}     (client sends both right after GAMEVERSION matches)
S  (on PLAYER_INFO)  NET_CLSV_SVCL_PLAYER_INFO echoed to all, playerIP filled in
S  (on PLAYER_INFO, Pro)  NET_SVCL_HASH_SEED {s1..s4}     to the client; starts a 10 s timeout
S  (on GAMEVERSION_ACCEPTED) password check; then the state dump:
     NET_SVCL_SERVER_INFO                                 one
     NET_SVCL_GAME_STATE {roundState, reInit=0}           one
     NET_SVCL_SV_CHANGE × 60ish ("set sv_... value")      one   (GameVar::sendSVVar, §2.6)
     NET_SVCL_PLAYER_ENUM_STATE for every other player    one
     NET_CLSV_SVCL_PLAYER_PROJECTILE for every live projectile   one
     NET_SVCL_FLAG_ENUM                                   one   (CTF only)
C  NET_SVCL_HASH_SEED_REPLY
```

Details:

- `NET_SVCL_NEWPLAYER` goes to **everyone**, including the new client. A client that has no `thisPlayer`
  yet takes the first `NEWPLAYER` it receives as itself (`ClientRecv.cpp:239`).
- Version check is client-side: the client compares `gameVersion` with its `GAME_VERSION_CL` (21100 in the
  Pro build, `Client.h`); on mismatch it disconnects itself.
- `NET_CLSV_SVCL_PLAYER_INFO` (`ServerRecv.cpp:439`): requires `players[playerID]`; truncates the name at 31
  chars, stores it, overwrites `playerIP` with the server's view of the address, echoes the struct to all
  (account `username`/`password` and `macAddr` included, as the original does). Then: queues a Pro
  checksum query (§ below), sends an account-auth HTTP request (skip), asks the master about cache bans when
  public and the IP is not `192.168.*`/`127.0.0.1` (skip), and records the player in the 50-entry
  `CachedPlayers` ring (name, IP, MAC; only used by console ban tools).
- `NET_CLSV_GAMEVERSION_ACCEPTED` (`ServerRecv.cpp:305`): if `sv_password != ""` and the given password
  differs (`CString` `!=` is **case-insensitive**, `stricmp`) → disconnect, nothing else. Otherwise the state
  dump above. Note the server does not remember that the password check passed; a client can send this
  message again (the client does, after a map download) and gets a fresh dump.
- `net_svcl_server_info.mapSeed` is always 0.
- `PLAYER_ENUM_STATE.weaponID` = the current weapon if alive, else `WEAPON_SMG` (0). Skin copied with
  `len<=6 ? len+1 : 7` bytes (the rest of the 7-byte field is garbage in the original; send zeros).
- Projectiles in the dump get `weaponID` by type: rocket → 5 (bazooka), grenade → 8, molotov → 9,
  flame → −2, everything else → −1; `nuzzleID = 0`.
- **Checksum query** (Pro, `ChecksumQuery.h`): four random shorts `rand()%60000 + 10` sent as
  `NET_SVCL_HASH_SEED`; the reply is validated by md5 of the server's own `./bv2.exe` XOR seeds, but in the
  `LINUX64` build (and openbv's) `isValid` returns true. A query without a reply within 10 s (accumulated
  `delay`, checked each frame, `> 10.0f`) **disconnects the player** (with `NET_SVCL_PLAYER_DISCONNECT`).
  A failing reply inserts the player into the `BadChecksum` table. Go: send the seed, accept any reply,
  keep the 10 s timeout (openbv's client always replies).
- The client stops processing most messages until it has the server info (`ClientRecv.cpp:76`: only
  `NEWPLAYER`, `GAMEVERSION`, `SERVER_INFO`, `PING`, `MAP_CHUNK` pass before that). Anything else sent
  earlier is dropped by the client — order matters.

### 2.3 Map download

If the client does not have the map (`SERVER_INFO.mapName`), it sends `NET_CLSV_MAP_REQUEST {mapName,
uniqueClientID}` and waits. The server appends a transfer `{babonetID of sender, mapName, chunk 0}`
(`ServerRecv.cpp:45`). Each frame (`Server.cpp:1342`): for each transfer, while
`bytesSent <= sv_maxUploadRate*1024/30` (default 8 KB/s → 273 bytes/frame; the check is `bytesSent >
bytesPerFrame` *before* sending, so at least one chunk per frame per transfer list position):
read 250 bytes at `250*chunkNum` from `main/maps/<name>.bvm`, send `NET_SVCL_MAP_CHUNK {size, data}`,
`bytesSent += 250`; if `size != 0` keep the transfer with `chunkNum+1`, else drop it. The final chunk has
`size == 0` (a read at EOF) and tells the client the map is complete; it then sends
`NET_CLSV_GAMEVERSION_ACCEPTED` again. Quirk: `mapName` comes from the client unchecked (path traversal in
the original: `main/maps/<anything>.bvm`); the Go server must only serve maps from its map directory. A
missing file crashes the original (`fclose(NULL)`); Go: end the transfer.

### 2.4 Teams and spawning

`NET_CLSV_SVCL_TEAM_REQUEST` (`ServerRecv.cpp:628`): `newTeam = assignPlayerTeam(playerID, requested)`
(§5.13 for auto-assign). If the team changed: if the old team was red/blue and the player has played
(`timePlayedCurGame > EPSILON`, EPSILON = 0.0001): cache stats, `reinit()` (stats to zero). Then echo the
request **with `teamRequested = newTeam`** to all. If unchanged: nothing is sent. `assignPlayerTeam` itself
kills the player silently (`kill(true)`) and sets `timeToSpawn = sv_timeToSpawn` when the team changes.

`NET_CLSV_SPAWN_REQUEST` (`ServerRecv.cpp:667`), only while `roundState == GAME_PLAYING` and the player
exists:

1. If `sv_validateWeapons` (default true): the primary must be one of 0..7 and the secondary one of 10, 11,
   12, 13 (minibot, Pro); otherwise the server does `sayall "<name> is trying to hack his primary
   weapon! Kicked him"` (or secondary) and kicks.
2. If `!sv_enableMinibot` and secondary == minibot → knives.
3. Store `nextSpawnWeapon`/`nextMeleeWeapon`, call `spawnPlayer` (§5.9). The server does **not** check that
   the player is dead or that the respawn time elapsed; a spawn request from a living player respawns it.
4. On success: broadcast `NET_SVCL_PLAYER_SPAWN` with the request's skin and decals, the weapons, and the
   chosen position **×10**; then store the skin (truncated to 6 chars) and decals (÷255).

Spectators (team −1) and players without a team never spawn (`spawnPlayer` returns false; nothing is sent).

### 2.5 Movement: coord frames

Client → server, `NET_CLSV_SVCL_PLAYER_COORD_FRAME` (`ServerRecv.cpp:777`), sent by the client every
`max(avgPing, sv_minSendInterval)` frames while alive (`PlayerUpdate.cpp`), "UDP":

1. *(Pro)* If `!sv_beGoodServer` (default true, so normally skipped), the player is on a team, not holding
   the sniper, and `camPosZ >= 9`: schedule a kick in 7 s (camera-zoom hack).
2. Only if the player is alive and `babonetID` matches: `timeIdle = 0`; speed-hack check (§5.10); then
   `setCoordFrame` (`Player.cpp:1505`): ignored if the frame is older than the last one
   (`netCF1.frameID > frame.frameID`); otherwise `netCF0 = currentCF` with `netCF0.frameID = netCF1.frameID`,
   `cFProgression = 0`, `currentCF.vel = frame.vel/10`, `currentCF.camPosZ = frame.camPosZ`,
   `netCF1 = {frameID, position/100, vel/10, mousePosOnMap/100}`, and if `netCF0.frameID == 0` then
   `netCF0 = netCF1`.
3. If the player is not alive: reset the speed-hack counters.

Every server frame while alive, `Player::update` interpolates `currentCF` from `netCF0` to `netCF1`
(`CoordFrame::interpolate`, `Player.h:78`), then forces `position[2] = .25`:

```
cFProgression++
size = to.frameID - from.frameID
if cFProgression > size:
    if cFProgression < 15: position += vel * delay      (extrapolate with the last velocity)
    else:                   position = to.position
elif cFProgression >= 0:
    t = cFProgression / size;  animTime = size / 90
    if cl_cubicMotion:                                  (server's own cvar, default true)
        position      = cubicSpline(from.pos, from.pos + from.vel*animTime, to.pos - to.vel*animTime, to.pos, t)
        mousePosOnMap = cubicSpline(from.m, from.m + (to.m-from.m)*animTime, to.m - (from.m-to.m)*animTime, to.m, t)
    else:
        position = to.position; vel = to.vel
cubicSpline(x0,x1,x2,x3,t) = x0(1-t)^3 + 3x1 t(1-t)^2 + 3x2 t^2(1-t) + x3 t^3      (Helper.cpp:435)
```

The interpolated position is what hit tests, flag pickups, item pickups and radius damage use. Getting this
exactly right is essential for fidelity.

Server → clients (`Server.cpp:1133`), every frame while `GAME_PLAYING`, for each player *i*:
`sendPosFrame++`; when `sendPosFrame >= avgPing` **and** `>= sv_minSendInterval + nbPlayers/8` (integer
division; `nbPlayers` = players connected this frame): reset to 0 and send to *i*, for each other player *j*:

- if *j* is alive and *j ≠ i*: `NET_CLSV_SVCL_PLAYER_COORD_FRAME` with *j*'s `currentCF` (the
  interpolated one): `frameID` = *j*'s `currentCF.frameID` (the server's own per-player frame counter, which
  `Player::update` increments every frame; it is not the client's frame number), `position`×100,
  `vel`×10, `mousePos`×100, `babonetID`, `camPosZ = 0`.
- if *j* is alive and has a minibot (Pro): `NET_SVCL_MINIBOT_COORD_FRAME` (also for *j* = *i*).
- always (for every existing *j*, including *i* and dead players): `NET_SVCL_PLAYER_PING {j, ping}`.

then one `NET_SVCL_SYNCHRONIZE_TIMER {frameID (server frame counter), gameTimeLeft, roundTimeLeft}` to *i*.

Order: by *j* ascending (empty slots skipped), per *j* the coord frame, then the minibot frame, then the
ping; the timer last.

When a player's ping is "interrupted" (no pong for > 30 frames), the server freezes them at their last
received frame: `currentCF = netCF1` (keeping `currentCF.frameID`), `sendPosFrame = 0` (§5.11).

## 3. The baboNet layer and openbv's transport

The original baboNet (`src/engine/babonet/`) is TCP (+ optional UDP) with its own framing; `Server::host`
creates the server with `bb_serverCreate(false, MAX_PLAYER, sv_port)` (`Server.cpp:150`): **UDP disabled**,
so every message, including the ones sent with `NET_UDP`, goes over the reliable, ordered TCP stream.
openbv replaces it with WebSockets (`src/port/babonet_gasm.cpp`) and the Go server speaks that:

- One WebSocket connection per client: `ws://<host>:<port>/` (the client also accepts a full `ws://` or
  `wss://` URL as the host).
- Each baboNet packet = one binary message: `u16 typeID` (LE), `u8 protocol` (0 = TCP, 1 = "UDP" as the
  sender asked; informational), `u8 0`, then the packet bytes (possibly empty).
- Reliable and ordered, like the original's effective TCP-only behaviour.

Semantics the server code relies on, to reproduce in the Go session loop:

| baboNet call | Semantics |
|---|---|
| `bb_serverUpdate` | Returns **one** event per call: a new client's ID (> 0), a lost client's negated ID (< 0), 0, or an error. The original accepts pending connections only at half-second checks (`ConnCheck >= 0.5`), so a connection is admitted up to 0.5 s after it opens; `Server::update` calls it twice per frame (§1.3). |
| New client | Gets a NetID (1, 2, 3, … per server lifetime). The server then calls `createNewPlayerSV`. |
| Lost client | `updateNet` finds the player with that `babonetID`, cancels a vote against them (kick/ban by name or id → `VOTE_RESULT false`), deletes the player (the destructor drops a carried flag with `NET_SVCL_DROP_FLAG`), broadcasts `NET_SVCL_PLAYER_DISCONNECT`. |
| `bb_serverSend(data, size, type, dest, proto)` | `dest < 1` → all clients; else the client with that NetID (unknown → error, not sent). |
| `bb_serverReceive` | Packets oldest first. Each call scans the clients from the first and returns one packet from the first client that has one, so in one drain all of the first client's queued packets are processed before the second client's. Go: drain per-connection queues in connection order, each completely, then the next. (The original's client list order is the baboNet accept order; openbv's shim uses connection order.) |
| `bb_serverDisconnectClient` | Closes the connection; no lost-client event is reported for it (the server already deleted the player itself). |

**Ban by IP** is checked at connect (`updateNet`): the IP the transport reports (`IPDuGars`). Behind a
reverse proxy the Go server must take the client address from a trusted `X-Forwarded-For`.

The master-server connection and the peer channel are separate (§9).

## 4. The map format (.bvm) and the map queries

### 4.1 File format

`Map::Map` (`Map.cpp:44`, loader from `Map.cpp:217`). `FileIO` primitives (`FileIO.cpp`):
`getInt` = **16-bit signed** (`short`), `getUInt` = 16-bit unsigned, `getLong`/`getULong` = 32-bit,
`getFloat` = 32-bit, `getUByte` = 8-bit, `getVector3f` = 3 floats, little-endian. The map name is truncated
to 15 chars; the file is `main/maps/<name>.bvm`.

| Field | Type | 10010 | 10011 | 20201 | 20202 |
|---|---|:-:|:-:|:-:|:-:|
| version | u32 | ● | ● | ● | ● |
| author name | 25 bytes | | | | ● |
| theme | i16 | | | ● | ● |
| weather | i16 | | | ● | ● |
| width, height | i16, i16 | ● | ● | ● | ● |
| cells (row-major, y outer) | 2 bytes each | ● | ● | ● | ● |
| flagPodPos[0], [1] (blue, red) | vec3 ×2 | | ● | ● | (in CTF block) |
| objective[0], [1] | vec3 ×2 | | ● | ● | (in SND block) |
| dm_spawns | i16 count + vec3 × n | | ● | ● | ● |
| blue_spawns | i16 count + vec3 × n | | ● | ● | (in SND block) |
| red_spawns | i16 count + vec3 × n | | ● | ● | (in SND block) |
| game-type blocks | 4 × (i16 id + data) | | | | ● |

Cell bytes: byte 0: bit 7 = passable, bits 0–6 = wall height (a passable cell's height is unused by the
ray test's floor branch); byte 1 = dirt splat (client only). 20202 game-type blocks, `GAME_TYPE_COUNT = 4`
of them in any order: id 0 (DM) and 1 (TDM): no data; id 2 (CTF): flagPodPos[0], flagPodPos[1]; id 3 (SND):
objective[0], objective[1], blue spawn list, red spawn list; unknown id: logged, no data consumed (the file
is then misread — keep the behaviour). Any other version: nothing is read, the map has size 0 and no
cells (the original would crash on use; Go: reject as invalid).

Server-relevant derived data: `cells`, `size`, `dm_spawns`, `flagPodPos`, `objective`, the spawn lists;
`flagPos[2]` starts uninitialised (only meaningful once a flag is dropped), `flagState = {-2, -2}`.

There is also a 3D-model path (`main/modelmaps_______/<map>/<map>LM.DKO`, `dko_mapLM`) that changes ray tests;
the directory name is deliberately broken and no shipped map uses it. The Go server ignores it.

### 4.2 `IsMapValid` (`Map.cpp:1740`)

DM, TDM: at least one dm spawn. CTF: at least one dm spawn and both flag pods non-zero. Type 3 (Pro
"Champion"): at least one dm spawn. A map that fails is refused at `host` and skipped during rotation.

### 4.3 Ray test (`Map::rayTest`, `Map.cpp:1434`; `rayTileTest`, `Map.h:415`)

`rayTest(p1, p2, normal)` returns true on a hit and moves `p2` to the hit point, sets `normal`.

1. `i = (int)p1.x`, `j = (int)p1.y`. If outside the map → **false** (no hit, `p2` unchanged). If the start
   cell is a wall and `p1.z < height` → `p2 = p1`, true (normal unchanged).
2. Direction `sens`: X or Y, positive or negative, by the larger of |Δx| and |Δy| (ties → Y).
3. Walk: stop with false when leaving the map or passing `(int)p2` along the main axis. In each step test
   the current cell and its two neighbours across the main axis (`j-1`, `j+1` for X; `i-1`, `i+1` for Y) with
   `rayTileTest`; advance the main-axis index by one and recompute the cross index from the line equation
   (`j = (int)(p1.y + Δy * percent)` with `percent = ((float)i - p1.x)/|Δx|` for +X, `(p1.x - (i+1))/|Δx|`
   for −X; symmetric for Y).
4. `rayTileTest(x, y)` on a cell `[x,x+1]×[y,y+1]`, height `h`:
   - passable cell: only the floor: if `p1.z > 0 && p2.z <= 0`, intersection at z = 0; hit if inside the cell
     (normal (0,0,1)). Otherwise no hit.
   - wall: top face if `p1.z > h && p2.z <= h`; then the four side faces, each when the segment crosses that
     face's plane in the right direction and the crossing point is within the face and below `h`:
     x = x1 from −X side → normal (−1,0,0); x = x2 from +X side → (1,0,0); y = y1 → (0,−1,0); y = y2 → (0,1,0),
     tested in that order, the first match wins.
   Note `percent` uses `fabsf` denominators and exact float comparisons; port expression by expression.

### 4.4 `segmentToSphere(p1, p2, c, r)` (`Helper.cpp:476`)

Closest point of segment p1–p2 to c; hit if `distSq <= r*r`, and then **`p2` is moved to that closest point**.
`u = (p2-p1)/|p2-p1|` (no guard for zero length: NaN, no hit).

- Collision radius 0.25, centre z = 0.25 (forced every frame on the server).

- `kill()` sets `status = DEAD`, `deadSince = 0`, deletes the minibot, drops carried flags

- `spawn(p)` (`Player.cpp:822`): alive, life 1, `timeToSpawn = sv_timeToSpawn`, `immuneTime =

  always a new instance; `switchWeapon` also sets the *global* `gameVar.cl_primaryWeapon`, quirk §8).
- `reinit()`: stats (`dmg kills deaths score returns damage flagAttempts timePlayedCurGame`), pings,
  `babySitTime = 5`, `pingOverMax = 0`, `spawnSlot = -1`.
- Per-frame player update on the server (`PlayerUpdate.cpp:53`): ping log; `timeIdle += delay` unless
  spectator; `babySitTime -= delay`; `mfElapsedSinceLastShot += delay`; protection, immunity count down;

  delay`; `timeInServer += delay`; alive → `timeAlive`, `timePlayedCurGame += delay`, minibot think,
  interpolation (§2.5), aim angle from `mousePosOnMap`; dead on a team → `timeToSpawn -= delay` down to 0.

### 5.3 Hitscan shot (`NET_CLSV_PLAYER_SHOOT`, `ServerRecv.cpp:944`; `Game::shootSV`, `Game.cpp:1221` and `:1359`)

Accepted if the shooter exists and is alive, or dead for less than 0.2 s (`timeDead < 0.2`).

Rate limit:

- Shotgun, sniper: if `mfElapsedSinceLastShot + 0.061 > fireDelay` → `shotCount = 1`,
  `mfElapsedSinceLastShot = 0`; else if `shotCount < (shotgun ? 5 : 3)` → `shotCount++`; else **drop**.
  Before that, sniper (Pro): `nbShot = (currentCF.camPosZ >= 10) ? 3 : 2` on the *player's weapon instance*.
- Others: if `mfElapsedSinceLastShot < fireDelay + 0.05` → `secondsFired += fireDelay` else
  `secondsFired = 0`; then if `mfElapsedSinceLastShot + (chain gun ? 0.04 : 0.051) > fireDelay` →
  `mfElapsedSinceLastShot = 0`, else **drop**.
- `fireDelay` is looked up as `gameVar.weapons[playerShoot.weaponID]` — the **client-supplied** weapon ID,
  not the player's weapon (quirk; also unchecked bounds: Go must reject IDs outside 0..13). The shot itself
  then uses the player's *actual* weapon (`player->weapon`).

### 5.4 Damage (`Player::hitSV`, `Player.cpp:1111`)

```
cdamage = damage
if damage == -1:
    if sv_serverType == 1: SMG sv_smgDamage, sniper sv_sniperDamage, shotgun sv_shottyDamage,
                           DMG sv_dmgDamage, CG sv_cgDamage, other weapon.damage
    else: weapon.damage
if photon and sv_serverType == 1 and from != this:
    d = |position - from.weapon.shotFrom|
    sv_photonType 1: cdamage *= Vs + C*(PI/2 - atanf((d - Hs)*M))
                  2: cdamage *= Vs + C/((d - Hs)*M)                (d == 0 → 1e-58 (float: 0 → inf))
                  3: cdamage *= Vs + C/(1 + pow((d - Hs)*M, 2))    (pow in double)
                  else: cdamage *= C
    with C = sv_photonDamageCoefficient, Vs = sv_photonVerticalShift, Hs = sv_photonHorizontalShift,
         M = sv_photonDistMult;  PI = 3.141593f
if flame thrower and sv_serverType == 1 and from != this:
    cdamage = sv_ftDamage * (1 - |position - from.weapon.shotFrom| / sv_ftMaxRange)
if protection > 0.6: cdamage *= 0.5
if immuneTime > 0.3: cdamage = 0
if sv_subGameType == INSTAGIB (1) and weapon not grenade/knives/molotov: cdamage = life
if not alive: return
```

Then two branches:

**Same team and game type is not DM and not type 3** (`from.teamID == teamID`):
- If `sv_friendlyFire` or self-damage (`from == this`): `from.dmg += min(cdamage, life)` (if not self),
  `life -= cdamage`, `screenHit += cdamage`, broadcast `NET_SVCL_PLAYER_HIT {playerID, fromID, weaponID,
  damage = life (remaining), vel = (0,0,1)}`.
- If `sv_reflectedDamage` and not self: `from.hitSV(weapon, from, cdamage)` (the shooter takes the same
  damage, as self-damage, recursively through these rules).
- If `life <= FLT_EPSILON` (1.1920929e-7): death (below) and then scoring:
  DM-branch never applies here; for TDM: the *killer's team* score −1; `from.deaths++`; if not CTF:
  `from.score--`. (The victim's deaths are **not** incremented; the killer gets the death — quirk.)

**Otherwise** (enemies, DM, type 3, or a team player without a team…):
- `from.dmg += min(cdamage, life)` (not self), `life -= cdamage`, `screenHit`, broadcast `PLAYER_HIT` as above.
- If `life <= FLT_EPSILON`: death, then scoring: if `from != this`: unless CTF, the killer's team score +1
  (blue/red by `from.teamID`) and `from.score++`; `from.kills++`, `deaths++`. If self-kill:
  `from.deaths++`, unless CTF `from.kills--` and `from.score--`.

Death (both branches, server only): spawn drops at the victim's position (§5.7: one life pack, one dropped
weapon with the victim's weapon ID, one dropped grenade per `nbGrenadeLeft`), each also broadcast as
`NET_CLSV_SVCL_PLAYER_PROJECTILE`; then `kill(true)`. With `sv_showKills` the dedicated server logs
`"Player id:%d killed player id:%d with weapon id:%d"`.

`NET_SVCL_PLAYER_HIT.vel` is always the raw chars `{0, 0, 1}` (the client divides by 10: a 0.1 m/s nudge
upwards). Send exactly those bytes.

### 5.5 Radius damage (`Game::radiusHit`, `Game.cpp:1592`)

`radiusHit(pos, radius, fromID, weaponID, sameDmg)`: only if `players[fromID]` exists. For every player *i*
(dead ones too — `hitSV` ignores them; knives skip the attacker): `d = |pos_i - pos|` (3D);
if `d < radius` and **no** `rayTest(pos, pos_i)` hit (line of sight): `hitSV(weapon, attacker,
damage = (sameDmg ? 1 : 1 - d/radius) * weapon.damage)`. Self-damage applies (rockets, grenades, nukes).

| Source | radius | damage | sameDmg |
|---|---|---|---|
| Knives (`shootMeleeSV`) | 1 | 0.60 | yes |
| Grenade explosion | 3 (visual radius 1.5) | 1.5 × (1−d/3) | no |
| Rocket | 3, or `sv_zookaRadius` (2.0) when `sv_zookaRemoteDet && sv_serverType == 1` | bazooka damage (0.85 after the bug, §8) | no |
| Molotov flame tick | 0.5, every 20 frames | 0.15 × (1−d/0.5) | no |
| Nuke bot | `sv_nukeRadius` (6) | 8.0 × (1−d/6) | no |
| Console `nuke`/`nukeall`, exploding FT | `sv_nukeRadius` | 8.0 × (1−d/r) | no |

### 5.6 Projectiles (`GameProjectile.cpp`)

Creation from a client request (`NET_CLSV_SVCL_PLAYER_PROJECTILE`, `ServerRecv.cpp:1025`):

1. Shooter alive, or dead < 0.2 s and the projectile is a grenade, molotov or rocket.
2. Molotov and `!sv_enableMolotov` → drop.
3. Rocket: the shooter's current weapon must be the bazooka, else drop. If `sv_zookaRemoteDet &&
   sv_serverType == 1` and the shooter has a rocket in the air and `mfElapsedSinceLastShot > 0.25`: set
   `detonateRocket = true` and drop (the second press detonates).
4. Weapon IDs other than grenade/molotov: if `mfElapsedSinceLastShot + 0.1 > weapons[weaponID].fireDelay`
   create (else drop); rockets set `rocketInAir`; `mfElapsedSinceLastShot = 0`. Grenade/molotov: create
   (no rate check; the count check is in `spawnProjectile`).
5. Echo the request to **all** (including the sender) with the `uniqueID` the server assigned.

The server accepts any `projectileType` from a client (no check that it is a rocket/grenade/molotov); a
client can request a life pack or a flame. Faithful; the hardening option of §1.4 could restrict client
requests to types 2, 3, 7.

`Game::spawnProjectile(pp, imServer=true)` (`GameSpawn.cpp:430`): `uniqueProjectileID++` (a global counter,
starting at 0, never reset), `pp.uniqueID = it`; grenade: needs `nbGrenadeLeft > 0` (then `--`), molotov:
`nbMolotovLeft > 0`; position = pp.position/100, vel = pp.vel/10; `fromID` = `pp.playerID`, except dropped
weapons where `fromID` = `pp.weaponID` (the weapon carried, reused field); push back; `projectileID` = index.
If the new projectile is a flame, the server itself broadcasts it (`weaponID = 9`).

11. Rocket (server-owned, not yet deleted): `playerInRadius(position, 0.25)` (i.e. within 0.5 of a player

### 5.8 Melee and secondaries (`NET_CLSV_SVCL_PLAYER_SHOOT_MELEE`, `ServerRecv.cpp:139`; `Weapon::shootMeleeSV`, `Weapon.cpp:449`)

Alive players with a melee weapon: `shootMeleeSV`, then echo the message to all. **No rate limit.**

- Minibot (Pro, `SpawnMiniBotSV`): if no bot and no wall between the player and one metre towards the aim:

### 5.9 Spawn points (`Game::spawnPlayer`, `GameSpawn.cpp:144`)

Only for blue/red players with a map; DM/TDM/CTF use the map's `dm_spawns`:

- DM: for each spawn *i*: `nearest` = min `distSq` to any *other* alive player (initial 100000); keep the
  spawn with the largest `nearest` (strictly greater than the best so far, starting at 0); but if there is
  no other alive player (`nbPlayer == 0` — evaluated per spawn, so it triggers on the first spawn checked):
  `bestFound = rand() % spawnCount` and stop.
- TDM, CTF: the same, counting only alive players of the *other* team.
- Pro, CTF with `spawnType == LADDER (1)`: in the first 10 s of the game (`sv_gameTimeLimit -
  gameTimeLeft < 10`) spawn on the own flag pod (`flagPodPos[teamID]`).
- Type 3 "Champion" (Pro): each player keeps a `spawnSlot`: the first slot index 0..31 not used by another
  team player; spawn at `dm_spawns[slot*5 + rand(0, 5)]` (`rand(int,int)` = `from + rand() % (to-from)`,
  so 0..4), clamped (`> size` → last; note `> size` not `>= size`: index == size is out of bounds in the
  original; Go: clamp to `size-1` for both).
- The position is `(spawn.x, spawn.y, 0.25)`.

### 5.11 Ping, timeouts, idling

Per frame per player (`Server.cpp:1027`): if not waiting for a pong: when `currentPingFrame >= 30`: reset to
0, `waitForPong = true`, `connectionInterrupted = false`, send `NET_SVCL_PING {playerID}`, and skip the
increment this frame. If waiting: `ping = max(ping, currentPingFrame)`; at `> 30` frames: freeze the player
(`currentCF = netCF1`, keep `frameID`), `connectionInterrupted = true`, `sendPosFrame = 0`; at `> 300` frames
(10 s; the comment says 3 s): cache stats, disconnect ("no respond since 3sec"), delete, broadcast
`PLAYER_DISCONNECT`, skip. Then `currentPingFrame++`. On `NET_CLSV_PONG`: if waiting, `waitForPong = false`,
`ping = currentPingFrame`. `ping` is in **frames** (1 frame ≈ 33 ms).

`updatePing` (every frame, `PlayerUpdate.cpp:29`): every `1/30 s` (a separate timer; effectively every
frame) log `ping` in a 60-entry ring, `pingSum += new - (entry after it)`, `avgPing = max(pingSum/60, 1)`.
`avgPing` paces the coord-frame sends (§2.5).

Max ping (`Server.cpp:1087`): if `babySitTime <= EPSILON` and `ping*33 > sv_maxPing` (ms) and `sv_maxPing != 0`:
`pingOverMax += delay`; over 5 s (`maxTimeOverMaxPing`): `sayid <id> Maximum ping exceeded, moving to
spectator`, `moveid -1 <id>`, `pingOverMax = 0`. Else `pingOverMax = 0`.

Idle (`sv_autoSpectateWhenIdle`, default true): a red/blue player with `timeIdle > sv_autoSpectateIdleMaxTime`
(180 s; `timeIdle` counts while dead too and is only reset by coord frames, which dead players do not send)
is moved to spectator with `moveid -1 <id>`.

Join message (`sv_sendJoinMessage`): when `1.0 < timeInServer < 1.0 + delay`: `sayid <id> <sv_joinMessage>`
(a private chat, `teamID = -3`, text `"\x08Server: <message>"`, §7). (The listen server has no `sayid`
command and prints "Unknown command".)

### 5.12 Round and game end (`Server.cpp:828`)

Checked every frame while `GAME_PLAYING`:

| Type | Ends when | Result state |
|---|---|---|
| DM (0) | time out (`gameTimeLeft == 0 && sv_gameTimeLimit > 0`); any player `score >= sv_scoreLimit > 0` | `GAME_DONT_SHOW (3)` |
| TDM (1) | `blueScore == redScore >= limit` → DRAW (2); `blueScore >= limit` → BLUE_WIN (0); `redScore >= limit` → RED_WIN (1); then time out → DONT_SHOW (overrides) | as listed |
| CTF (2) | `blueWin == redWin >= sv_winLimit` → DRAW; blue/red `>= sv_winLimit` → win; time out → compare wins (draw / higher wins) (overrides) | as listed |
| 3 | as CTF, with `blueWin`/`redWin` — which nothing increments in the Pro build, so in practice only the time limit ends it, as a DRAW | as listed |

On end: (report upload, skip), clear the stats cache, `changeMapDelay = 10`, `nextMap = queryNextMap()`,
broadcast `GAME_STATE {state, reInit = 0}`. While not `GAME_PLAYING` players are not updated (timers frozen),
spawn requests are refused, coord frames are not broadcast, but projectiles keep updating.

Map rotation (`Server::queryNextMap`, `Server.cpp:363`): maps added to `mapList` since the last call get a
`mapInfo {name, area = passable cells excluding the border, lastPlayed = 1e9}` (loading each map); for every
map: the current one gets `lastPlayed = 1`, the others `lastPlayed++`; among *suitable* maps (§ below) pick
the largest `lastPlayed` (first on ties); none suitable → `rand(0, n)` = `rand() % n` over all (note
`rand(int,int)` excludes the upper bound: with n = count-1 the last map is never picked, and with one map
`n = 0` → `rand(0,0)` returns 0). The chosen map gets `lastPlayed = 0`. Suitable
(`filterMapFromRotation`): `tilesPerBabo = area / max(2, red+blue players)` within
`[sv_minTilesPerBabo, sv_maxTilesPerBabo]` (max 0 = no upper limit).

### 5.13 Teams and balance

`assignPlayerTeam(id, requested)` (`Game.cpp:880`): `spawnSlot = -1`; auto-assign (2): count other players
on blue and red; more red → blue; more blue → red; equal → the team with the lower score (`blueScore <
redScore` → blue, `>` → red), equal scores → `rand() % 2 == 0 ? blue : red`. If the player's account is not
approved for that team (`isApproved`, all approved by default) → spectator. On a change: `kill(true)`,
`timeToSpawn = sv_timeToSpawn`, log the move. Returns the team.

Auto-balance (TDM, CTF, `sv_autoBalance`, `Server.cpp:1234`): when the timer is 0 and the team sizes differ
by 2 or more: `autoBalanceTimer = sv_autoBalanceTime`, broadcast `NET_SVCL_AUTOBALANCE`. When the timer runs
out: move `bigger - smaller - 1` players from the bigger team: candidate = the last player of that team (in
slot order) — skipping one carrying the enemy flag — then the one with the *least* `timePlayedCurGame`
scanning downwards; `teamID = assignPlayerTeam(...)`, broadcast `TEAM_REQUEST {id, newTeam}`. (The flag
check compares `flagState[1]` for blues and `flagState[0]` for reds, i.e. the flag that team carries.)

Two details of the timer and the loop (kept): the countdown fires on `autoBalanceTimer < 0` after the
decrement, so a timer that lands exactly on 0 is taken up again by the `== 0` branch the next frame (a
recount and possibly a new notification, no balance); and the red/blue lists are built once before the
`while (nbToSwitch > 0)` loop, so with more than one player to move every pass picks the same player from the
unchanged list: he is moved once (`assignPlayerTeam` to his new team changes nothing) and the
`TEAM_REQUEST` is sent again. With teams 2 apart (one to move), the usual case, it makes no difference.

### 5.14 CTF (`Server::updateCTF`, `ServerCTF.cpp:24`)

Flags: 0 = blue (at `flagPodPos[0]`), 1 = red. `flagState`: −2 at its pod, −1 on the ground at `flagPos`,
≥ 0 carried by that player. Positions compared in 2D (`(x, y, 0)` against the 3D pod/flag position, so a
pod with z ≠ 0 shifts the test). Each frame, each block at most **one** event (`break` after it):

- Blue flag at home (−2): a red player within **0.25** of `flagPodPos[0]` takes it (`flagState[0] = id`,
  `CHANGE_FLAG_STATE {0, id, id}`, `flagAttempts++`). In the same loop: a blue player carrying the red flag
  (`flagState[1] == id`) within 0.25 of `flagPodPos[0]` **scores**: `flagState[1] = -2`,
  `CHANGE_FLAG_STATE {1, -2, id}`, `score++`, `blueWin++`, `blueScore = blueWin`.
- Blue flag on the ground (−1): a red player within **0.5** of `flagPos[0]` takes it; a blue player within
  **0.5** returns it (`-2`, `returns++`).
- Red flag at home: a blue player within 0.25 of `flagPodPos[1]` takes it; a red carrier of the blue flag
  within 0.25 of `flagPodPos[1]` scores for red (`redWin++`, `redScore = redWin`).
- Red flag on the ground: a blue player within **0.25** takes it; a red player within **0.25** returns it
  (the log says "returned the blue flag" — bug).

So capturing needs your own flag at home, and the radii are asymmetric (0.5 for the blue flag on the ground,
0.25 everywhere else). Clients mirror: `-1 → -2` = return (`returns++` on the client), `-1/-2 → id` = take
(`flagAttempts++`), `→ -2` otherwise = capture (scores and wins +1 for the *other* flag's team, `score++`).

### 5.15 Type 3 "Champion" (Pro)

The Pro build calls game type 3 "Champion" (`sv_gameType` help text). Spawning per §5.9; scoring as DM
(team scores still count kills by the killer's team); `updateSnD` is empty in Pro. Each frame
(`Server.cpp:1279`): when `roundTimeLeft == 0`: `roundTimeLeft = sv_roundTimeLimit`, every `spawnSlot =
-1`, and for every red/blue player broadcast `PLAYER_HIT {id, fromID = id, weaponID 0, damage = -100, vel
(0,0,1)}` — the clients kill them, **the server does not** (its players stay alive). Faithful, but note
it.

### 5.16 Votes (`Game.h` `SVoting`, `ServerRecv.cpp:60`, `:94`, `Game.cpp:355`)

- Request (`NET_CLSV_SVCL_VOTE_REQUEST {vote text, playerID}`): if a vote runs → warn, ignore. If not
  `validateVote(text)` → ignore. Else: every player `voted = false`; `castVote`: active voters = players on
  red/blue (their babonetIDs; others `voted = true`), results 0/0, 30 s; `votingFrom` = the requester's
  name; echo the request to all. (`sv_enableVote` is **not** checked here, only for ballots — a quirk:
  votes can be started but not answered when voting is disabled; they then time out and fail.)
- `validateVote`: the first token (or for `set sv_x ...` the variable name), lower-cased, must be in
  `voteList` (built with the console `voteon <command>`; empty by default → no vote is valid).
- Ballot (`NET_CLSV_VOTE {value, playerID}`), only with `sv_enableVote`: if the player has not voted and
  is an active voter: count it, broadcast `UPDATE_VOTE {yes, no}`.
- Each frame: `remaining -= delay`; ends at 0, or when yes > voters/2, no > voters/2, or all voted. Then
  broadcast `VOTE_RESULT {passed = yes > voters/2}` and if passed run the text as a console command.
- A vote to kick/ban a player who disconnects ends with `VOTE_RESULT false` immediately (but the vote stays
  "in progress" on the server — quirk: no new vote can start until it times out).

### 5.17 Chat (`ServerRecv.cpp:552`)

`message[129] = 0`, log it. `teamID == -2` → all; `-1` → spectators only; `0` → blue only; `1` → red only;
any other value → nobody. (Clients send −2 for "all", their team for team chat.) The server's own
`sayall` uses `teamID = PLAYER_TEAM_SPECTATOR - 1 = -2` and prefixes `"console : \x08"`; `sayid` sends
`teamID = -3` (clients show `teamID < -1` to everyone they receive it, i.e. the one recipient).
Messages are at most 129 chars + NUL.

## 8. Randomness, timing and quirks to preserve

### 8.1 RNG

All game randomness uses C `rand()` through the helpers in `CVector.cpp`:

- `rand(int from, int to)` = `from == to ? from : from + rand() % (to - from)` (after swapping so from ≤ to):
  **upper bound excluded**.
- `rand(float from, float to)` = `eccart = to - from; precision = 30000 / eccart; eccart == 0 ? from :
  from + (rand() % (int)(eccart * precision)) / precision` — `(int)(eccart*precision)` is 30000 (or 29999 by
  float rounding); **no `rand()` call when from == to** (`rand(-0, 0)` for zero spread).
- Vector `rand(a, b)` = component-wise float rand, x then y then z.

The Windows dedicated server used MSVC's `rand()`: `seed = seed*214013 + 2531011; return (seed >> 16) &
0x7fff` (RAND_MAX 32767). Seeded with `srand(time(0))` in `Server::host` and in every `Game::createMap`.
The Go server should implement exactly this LCG (one generator per session, seeded from the clock, with a
test hook to fix the seed) and call it at exactly the same points, in the same order, so the distributions
(`% 30000` on a 15-bit value) match. Consumers on the server: shot spread (2 calls per pellet), shotgun range
variation, spawn choice, auto-assign ties, drop velocities (2 per item), molotov flame velocities (3+3),
checksum seeds (4), map rotation fallback, map seed (`rand() % 1000000`, unused).

### 8.2 Timing

Fixed 30 Hz steps; float `delay = 1/30`. Frame-counted timers are listed in §1.2. The original's catch-up
loop runs several updates back to back after a stall; the Go ticker should do the same (cap the catch-up,
e.g. at 10 steps, and log stalls).

### 8.3 Quirks to keep (behaviour clients depend on or players knew)

1. **`if (gameVar.sv_serverType = 1)`** (`GameProjectile.cpp:718`): every projectile update on the server (and
   on clients) sets `sv_serverType` to 1 and the bazooka damage to `sv_zookaDamage`. From the first projectile
   on, the server plays by Pro rules (Pro damage table, photon and flame-thrower formulas, rocket radius)
   whatever `sv_serverType` was set to, without telling clients (new joiners get `sv_serverType 1`).
2. Hitscan hits the **last** intersected player by slot index, not the nearest (§5.3).
3. Beam weapons hit every player along the beam; the photon hits again ten times over 30 frames.
4. Team-kill bookkeeping gives the death to the killer, not the victim (§5.4).
5. Asymmetric CTF radii and the wrong return message (§5.14).
6. Spawn position in `PLAYER_SPAWN` is ×10, everything else ×100.
7. `NET_CLSV_SVCL_PLAYER_UPDATE_SKIN` is broadcast once per connected player.
8. Molotov flames on a player hit both have zero velocity (§5.6).
9. Fire-rate checks use the client-supplied weapon ID.
10. Melee has no server-side rate limit (knife spam is limited only by the client).
11. A spawn request from a living player respawns it; the server does not enforce the respawn timer.
12. Flame stick messages address projectiles by vector index, sent twice on release.
13. Votes can be started with voting disabled; a kick vote whose target leaves blocks new votes until it times out.
14. `switchWeapon` writes the global `gameVar.cl_primaryWeapon`; the next new player's default
    `nextSpawnWeapon` is the last weapon anyone switched to (harmless: spawns always carry the weapon).
15. Type 3 round reset kills players on clients only.
19. Auto-balance re-sends the same player's team change when more than one has to move (§5.13).
16. Projectile deletion takes one extra frame (the projectile is updated twice after being flagged).
17. `sv_password` sent to clients and the master in clear (**deviate**: don't).
18. The ping timeout is 300 frames (10 s), not the 3 s in the log text.

### 8.4 Bugs the Go server should *not* reproduce (document each)

Crashes and memory-safety bugs: out-of-range IDs from clients (`playerID`, `weaponID` index arrays without
checks — reject); `players[-1]` in `moveid`; `nuke` with an unknown name; the `sendSVChange` buffer overflow;
`fclose(NULL)` on a missing map; map name path traversal; `spawnLocation > size`; division by zero in
`segmentToSphere` for a zero-length segment (keep "no hit"). In each case the Go server should do what the
original does when the input is valid, and reject/clamp otherwise.

Deviations implemented so far (milestone 1, `server/internal/game`):

| Deviation | Why |
|---|---|
| `set sv_password ""` in the cvar dump, never the password | The original sent it in clear to every client (§2.6). |
| Messages naming a player that isn't the sender's own are ignored (`Options.BindPlayerID`, default on) | §1.4: a client could act for any player. |
| Client-supplied player IDs outside 0..31, weapon IDs outside the table (with `sv_validateWeapons` off), team requests outside −1..2 are refused | The original indexed its arrays with them. |
| Map downloads serve only plain names found in the map folder, case-insensitively; a missing file ends the transfer | Path traversal and `fclose(NULL)` (§2.3). |
| `PLAYER_ENUM_STATE` skin bytes after the string are zeros | The original sent uninitialised memory. |
| Champion spawn index clamped at `size-1` | The original's `> size` test let `size` through (§5.9). |
| The console `set` sends the formatted value after validation | The original broadcast the raw command line before validating it (§2.6). |

Milestone 2 (DM combat):

| Deviation | Why |
|---|---|
| `NET_CLSV_PLAYER_SHOOT` with a weapon ID outside 0..13, or from a player without a weapon, is dropped | The rate check indexed `gameVar.weapons[]` with the client's ID; a player that never spawned has no weapon (null dereference). |
| A pickup of a dropped "weapon" whose ID isn't a weapon still sends the pickup but doesn't switch weapons | `switchWeapon` indexed the table with it. |

Milestone 3 (projectiles and secondaries):

| Deviation | Why |
|---|---|
| `NET_CLSV_SVCL_PLAYER_PROJECTILE` with a weapon ID outside 0..13 (other than grenade/molotov) is dropped | The fire-delay check indexed `gameVar.weapons[]` with it. Any `projectileType` is still accepted, as in the original (§5.6). |
| A rocket whose shooter has left neither clears his flags nor reads his detonation request (it still flies and explodes) | `players[fromID]` was dereferenced without a check: the original crashed. |
| `Server::nukePlayer`'s explosion carries `playerID -1` | The original left the field uninitialised. |

The draws are the same; only which axis gets which changes, which no player can tell (the seed is the clock), and this order keeps the port checkable. |
| `Map::collisionClip` and `performCollision`: a neighbour index outside the cell array counts as a wall | The original read past the array (only possible for a bot pushed to the map's edge). Neighbours of edge cells still wrap into the next/previous row, as in the original. |
| A projectile of an unknown type (a client asked for type 0, 1 or 9+) lives 0 s and is deleted at once | The constructor left `duration` uninitialised for them. |

Arithmetic: all game maths is float32 with every product rounded on its own (Go may fuse `a*b+c` on arm64;
the C++ and the wasm client don't), `cosf`/`sinf` are musl's (`bvmath/muslmath.go`, the wasm client's libc:
a correctly rounded cosf differs in the last bit for some angles, and `(short)(x*100)` can turn that into a
different coordinate), and the C conversions to `char`/`short` truncate and wrap as the wasm build does.
`atanf` (photon falloff type 1) and `pow` (type 3) are Go's double functions rounded; the golden cases
match bit for bit, but the photon types are rarely used and untested on other inputs.

## 9. The master server (game list)

The in-game Game Browser (`CBrowser`, `CLobby`) gets its list from a master server (`CMaster.cpp`). In
openbv the master address comes from the launch parameter `master=host:port` (game port; `bv2.db` stores it
+1000 and `CMaster::GetMasterInfos` subtracts 1000, `src/port/sqlite_shim.cpp`); the connection uses the same
WebSocket transport (§3). The Go server should be the master for its own sessions (and can accept
registrations from other servers).

### 9.1 Client flow (`CMaster::requestGames`, `CMaster.cpp:904`)

1. Connect (if not connected), then send `BV2_LIST (999) stBV2list {Version "2.11"}` (from `bv2.db`
   `LauncherSettings.Version`).
2. Master replies `MASTER_INFO (1002) stMasterInfo {NbGames}`: −1 = outdated version (client prints
   "Outdated version" and disconnects), 0 = none (client disconnects), n = n rows follow.
3. Then `BV2_ROW (997) stBV2row` × n (134 bytes each).
4. The client pings each row in turn over the peer channel (`CPing`): openbv has no peer transport, so every
   ping times out after **1 s** and the game is listed with ping 1000. With many games the list fills at one
   row per second. (Improvement for later: a WebSocket ping to the session port, in the client's baboNet
   shim and the Go server.) After the last row the client disconnects from the master.

Row fields the client shows/uses (`CBrowser.cpp`): `serverName`, `map`, `nbPlayer`/`maxPlayer`,
`gameType`, `password` (only whether it is empty — **the password itself is sent to every browsing client**;
Go: send a placeholder like `"*"` for passworded games), `ip`, `port`, `Version`. Joining runs the console
command `connect <ip> <port>` → `ws://<ip>:<port>/`.

`ip` is 16 bytes (15 + NUL): a host name longer than 15 characters does not fit (`openbv.emdzej.pl` is 16).
Options: (a) the Go master puts the numeric IP; (b) leave `ip` empty and have openbv's client use the
master's host for an empty `ip` (a small change in `src/port/babonet_gasm.cpp` or `CBrowser`); recommended:
(b), with (a) as the fallback when the master knows a short public address.

### 9.2 Server flow (what a game server sends to the master)

- Every 20 s while `sv_gamePublic` (§1.3 step 1): `BV2_ROW` with `map`, `serverName = sv_gameName`,
  `password = sv_password`, `ip = ""` (the master fills in the connection's address), `port = sv_port`,
  `nbPlayer` (connected players, spectators included), `maxPlayer = sv_maxPlayer`, `flags 0`, `gameType`,
  `ServerID 0`, `Priority 0`, `DBVersion`. (`Version` is left uninitialised in the original.) The message
  stack is cleared before queueing, and `sendPacket` connects first if needed.
- On shutdown: `KILL_SERV (1001) stKillServ {Port}`.
- Optional, account-era: `CACHE_BANNED`, `USER_STATUS_UPDATE`, `STATS_UPDATE`, ...: ignore.

The Go master keeps a table of rows keyed by (address, port), expiring after ~60 s without an update, and
answers `BV2_LIST` with its own sessions plus registered ones. Unknown message types are ignored.

### 9.3 Sessions and ports

Each Go session is one BV2 server with its own port (`sv_port`), map rotation, cvars and players. Two ways
to expose them:

1. **One listener per session port** (`ws://host:<sv_port>/`) — exactly what the client builds from a row.
   Default.
2. **One HTTP listener with paths** (`/bv2/<port>` or `/bv2/<session id>`) behind a reverse proxy; needs the
   client to build URLs from a template (a launch parameter in openbv's client, e.g.
   `net_url=wss://openbv.emdzej.pl/bv2/{port}`).

The master listens on its own port (default 10207, matching the old master's game port if desired) or on the
shared HTTP listener at `/master`.

```
  internal/session/       Server: the frame loop (§1.3), recvPacket (§2), CTF, votes, rotation, bans,
                          console commands (§7)
  internal/master/        the master protocol (§9)
  internal/admin/         HTTP API + embedded web UI: sessions (create/stop/restart, cvars, rotation),
                          players (kick/ban/move/say), chat and console log, bans; auth (OIDC or a token),
                          audit log, rate limits (as ../nowhereinparticular/services/api)
  internal/reftest/       differential-test harness (§10.3)
```

Concurrency: one goroutine per session runs the 30 Hz loop and owns all game state; connections feed
per-connection queues read only by that goroutine (no locks in game code); the admin API talks to a session
through a command channel processed at the start of a frame (like console input).

### 10.3 Testing against the original

Three references, from cheapest to most faithful:

1. **Unit golden values from the C++ code.** For the bit-exact core (`bvmath`, `bvmap.rayTest`,
   interpolation, spawn choice, damage formulas), write small C++ drivers that link the original source files
   (`src/game/CVector.cpp`, `Helper.cpp`, `Map.cpp` parts, `GameVar` tables) natively and print results for
   tables of inputs; the Go tests compare. Use the MSVC LCG in both (replace `rand()` with a test
   implementation via a macro) and fixed seeds.
2. **The listen server in the openbv client.** Host a game in `openbv.wasm` (headless gasm-run with scripted
   input) and record every message its in-process server sends and receives (a logging hook in
   `src/port/babonet_gasm.cpp`, behind a launch parameter). Replay the recorded client messages, frame by
   frame, into a Go session with the same seed and compare the server's outgoing messages. The listen server
   differs from the dedicated one in the few places marked "listen" above (flame-thrower spread, `sayid`,
   kill logs); the comparison must account for them.
3. **The original dedicated server, native.** The repository's `Makefile` builds `bv2dedicated` for Linux
   with `-DCONSOLE -D_PRO_ -DLINUX64` from `BaboViolent2/Code/*.cpp` and the engine libraries `dkc dko dkt
   dksvar` plus the original `baboNet` (sockets), `sqlite3`, `curl`, `crypto`, `pthread`. To use it as a
   reference: build it in a Linux container (or on macOS with small fixes) from `ref/BaboViolent2`, patch
   `rand`/`srand` to the MSVC LCG with a fixed seed and `time()` to a fake clock advanced by the test, and
   drive it through a Go test client speaking the original **TCP baboNet framing** (`src/engine/babonet/`:
   a 9-byte key handshake, `"RND1"` + version + ids, then packets as `u16 size, u16 typeID, data` — see
   `cClient.cpp`, `cIncConnection.cpp`, `cPacket.cpp` for the exact handshake before implementing). The same
   scripted clients run against the Go server over WebSockets; per frame, the two message streams must match
   byte for byte (after zeroing padding). This is the strongest check and the one to automate in CI for the
   simulation milestones (2–4).

What exists (milestones 2–4):

- `server/internal/reftest`: level 1. `cpp/build.sh` extracts the original functions verbatim
